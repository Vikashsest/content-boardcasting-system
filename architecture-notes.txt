Content Broadcasting System – Architecture Notes

1. Authentication & RBAC
   The system uses JWT-based authentication.
   Users log in and receive a token, which is used to access protected routes.
   Role-based access control is implemented:

* Teacher: upload and view content
* Principal: approve/reject content

2. Subject-based System Design
   Each content is associated with a subject (e.g., Maths, Science).
   APIs support filtering by subject.
   Content rotation is handled independently per subject.

3. Upload Handling
   Content is uploaded using Multer.
   Files are stored locally in the uploads folder.
   File validation includes type (JPG, PNG, GIF) and size limits.

4. Approval Workflow
   Content lifecycle:
   uploaded → pending → approved / rejected

Only principal can approve or reject content.
Rejected content includes a rejection reason.

5. Scheduling & Rotation Logic (Important)
   Each content has:

* start_time
* end_time
* rotation_duration

Content is active only if current time is within start and end time.

Rotation is implemented using a timeline-based approach:

* Total duration of all active contents is calculated
* Current time is taken modulo total duration
* Active content is selected accordingly

This ensures continuous looping and fair distribution.

6. Database Design
   Main tables:

* Users (id, name, email, password, role)
* Content (title, subject, file info, status, scheduling fields)
* Content Schedule (for future scalability)

Relationships:

* One user can upload many contents
* Content is linked to a subject

7. Folder Structure

* controllers: request handling
* services: business logic
* models: database schema
* routes: API endpoints
* middlewares: auth and RBAC
* utils: helper functions

8. Middleware Usage

* authMiddleware: verifies JWT token
* authorizeRoles: restricts access based on role
* error handling middleware for centralized error management

9. Scalability Approach

* Can integrate Redis caching for live APIs
* Can move file storage to AWS S3
* Can introduce queues for heavy processing
* Can scale database using read replicas

This design ensures clean architecture, scalability, and real-world applicability.
